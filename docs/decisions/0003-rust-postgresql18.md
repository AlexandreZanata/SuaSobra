# ADR-003 — Rust Backend, PostgreSQL 18.6 and Native UUIDv7

Status: Accepted owner instruction. Date: October 9, 2026. Supersedes the Python/Django backend and PostgreSQL 17 choices in ADR-001/ADR-002; ADR-002 product scope and main integration CI remain authoritative.

## Decision

Replace the generated backend with a Rust modular monolith using Axum, Tokio and SQLx. Pin Rust 1.99.0 in `rust-toolchain.toml` and exact direct dependencies plus `backend/Cargo.lock`. Run PostgreSQL 18.6 locally and in CI. Persistent application primary keys use `uuid PRIMARY KEY DEFAULT uuidv7()` generated by PostgreSQL, including users, supplier resources, sessions, history, audit, replay and migration records. Foreign keys and API resource identifiers use UUIDs. SQLx's internal migration version remains an integer, as required by its migration protocol.

PostgreSQL 18 has native UUIDv7 generation; no UUID extension or application-side UUID generator is necessary. [Official UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html), [18.6 release notes](https://www.postgresql.org/docs/release/18.6/).

## Boundaries and retained behavior

Port account registration/login/logout/session/CSRF, PostgreSQL login limiting, actor scopes and ownership, supplier lifecycle commands, establishments, pickup-point validation/privacy/version history, integer money/quantity primitives, UTC intervals, immutable policies, transactional audit/outbox primitives and command replay. Use one explicit supplier command transaction boundary shared by HTTP and operations. Preserve lock ordering and database-level append-only history.

Keep password hashing off the async executor, with bounded concurrent password work, a bounded PostgreSQL pool and a request body limit. A single executable and database remain the minimum deployment. Rust is an engineering choice, not evidence of a measured user capacity: representative load tests and host measurements are still needed before a capacity claim.

Resolve two existing inconsistencies with ADR-002: supplier registration requires valid declared contact and operations approval, not an automatic verification email; active policy contains no payment timeout or monthly billing quota. Automatic email verification/recovery HTTP routes return structured `501 feature_deferred`. Hashed expiring single-use token primitives and imported token data remain available for a separately authorized future delivery task. Financial and advanced launch exclusions are unchanged.

## Data and API migration

Rust uses a new `suasobra` schema. Legacy Django tables in `public` remain untouched. New UUID resources change the API identifier contract from numeric IDs to UUID strings. `import-django` transactionally maps legacy IDs to PostgreSQL-generated UUIDv7, copies accounts/supplier/site/point/events/history/tokens/outbox, and preserves exact original records in private database tables. Historical audit/replay records remain preserved there rather than authorizing a replay under the new command protocol. Source history snapshots retain their original references; the ID map resolves them.

Django PBKDF2-SHA256/PBKDF2-SHA1 and Argon2 hashes remain verifiable. New passwords use Argon2id. Old Django sessions require login; no session or CSRF secret is reused. Migration refuses a nonempty Rust target and rolls back fully on invalid rows. Do not overwrite a PostgreSQL 17 data directory with an 18 server: use a logical backup/restore into an isolated 18.6 target, rehearse and compare counts first. The local 17 volume is preserved; the 18.6 service has its own named volume and port.

See [the migration runbook](../engineering/rust-migration.md) for exact limits, authorization boundaries, rollback and verification. No production migration, deployment or infrastructure spending is implied by this source conversion.

## Verification

Versioned Rust suites cover unit rules, HTTP security/contracts, persistence, rollback, native UUID versions and real-database contention. Legacy import tests exercise mapping, source preservation and all-or-nothing rejection. `make verify` runs documentation validation, formatting, Clippy with warnings denied and all Rust test targets. `make build` produces the release executable. CI reproduces these only on pull requests targeting `main`.
