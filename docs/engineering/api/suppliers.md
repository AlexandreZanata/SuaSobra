# Supplier API

Prefix `/api/v1/suppliers/`. All endpoints require a session; writes require CSRF and typed fields. IDs are UUID strings generated by PostgreSQL. Every write invokes the same `suppliers::execute` transaction boundary. An optional `Idempotency-Key` (1..128 characters) is scoped to actor, command and resource: identical input returns the original committed response; changed input returns 409; failed transactions leave no replay record.

## Registration and access

`POST /` accepts trade_name (required, <=255), tax_id (required, <=32), contact_email (valid declared email), contact_phone (required, <=32), optional legal_name (<=255), and business_type (bakery/restaurant/grocery/cafe/hotel/other, default other). Unknown fields are rejected. Owner must be active, adult-declared and not completely suspended. Automatic verified contact is not a launch prerequisite under ADR-002. Success 201 creates pending_approval/financial_eligibility=disabled, grants supplier_owner while preserving consumer role, and commits registration event/audit together.

`GET /` lists only the actor's suppliers; an active authorized moderator may list all. `GET /{supplier_id}/` requires owner/moderator. `GET /{supplier_id}/events/` applies the same authority and returns most recent events, including prior/resulting standing, actor, reason/evidence and timestamp. Lists currently return arrays capped at 100; pagination is a future explicit contract task before large datasets. Unknown resource is 404; outsider access is 403. A public UUID never confers ownership.

The private supplier response contains id, owner_id, trade_name, legal_name, tax_id, business_type, contact_email, contact_phone, standing, financial_eligibility, lifecycle reasons/review/closure timestamps and created_at/updated_at. No public supplier directory is implemented yet.

## Lifecycle commands

All paths below are `POST /{supplier_id}/<action>/` and return 200 with the updated supplier. Current standing is locked and checked; invalid transitions return 409. Required reasons must be nonblank.

- `approve/`: active moderator, pending_approval -> active; optional reason defaults to Checks passed. Clears rejection grounds and records approval plus standing-change events.
- `reject/`: active moderator, pending_approval -> rejected; required reason, optional reapplication_conditions; records rejection plus standing-change events.
- `reapply/`: owner only, rejected -> pending_approval; optional correction_notes, retaining the original rejection evidence.
- `warn/`: active moderator, active -> warned; required reason.
- `clear-warning/`: active moderator, warned -> active; optional reason defaults to Correction verified.
- `suspend/`: active moderator, any nonclosed standing -> suspended; required reason, optional RFC3339 review_date.
- `close/`: owner or active moderator, any nonclosed standing -> closed; required reason and persisted closure timestamp. History remains available.

No client can set standing, financial eligibility or owner directly. Approval never enables online payments. Existing creation behavior for multiple sites is retained for migration compatibility; the minimal launch UI will operate one site/location rather than expose advanced multi-site management.

## Establishments

`GET /{supplier_id}/establishments/` and `POST` require owner/moderator. Create accepts required name (<=255) and optional description, returning 201. A closed supplier cannot create a site. No publication or inventory is created by a site command. Point contracts are in [pickup points](pickup-points.md).
