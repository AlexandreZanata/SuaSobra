# Command and Contract Conventions

Current scope is [ADR-002](../decisions/0002-free-simple-launch.md). Payment-provider/subscription contracts described as extensions below are deferred; do not build financial endpoints now.

## Required command record

For each write command, document: name; actor/scope; input fields; owner objects; canonical UC/INV/EDGE references; accepted policy/time; prerequisites; allowed current/result states; locked consistency boundaries; quantity/money effects; audit/events; external follow-up; replay behavior; structured failure codes; and tests.

Commands returning rejection leave business state unchanged, except an explicitly declared failed-attempt/security observation. Commands recognizing a real exceptional receipt record its money even when fulfillment is rejected. Do not confuse a rejected commercial action with absence of an externally substantiated fact.

Idempotency is scoped to actor and command. Reusing a command identity with identical input returns the original outcome; conflicting input returns an explicit conflict. Store a canonical input digest and result only alongside successful committed effects. A failed transaction cannot leave a false successful replay record. Provider event identity and provider receipt identity are separate from client command identity.

## Contracts before routes

At a resource's API task, add its explicit request/response examples to `docs/engineering/api/`, and freeze them with contract tests. Describe ownership, status codes, state/amount fields, pagination, public versus private fields, error codes, and replay behavior. Validate typed Rust command fields rather than accepting arbitrary dictionaries.

The active route groups are authentication, suppliers/pickup points, future offers/discovery, reservations, pickup, reviews/cases and metrics. Payment, plans and advanced engagement groups remain deferred under ADR-002. Group naming is planning guidance; exact paths are specified once in their scoped contract task. Do not invent different paths separately in the web.

The launch browser records handover of goods and accepted direct-at-pickup price; it cannot initiate platform payments or claim provider-confirmed receipt. A moderation route cannot directly set a reputation percentage.

Use `/api/v1/` as the shared prefix, integer-cent monetary fields, ISO-8601 aware timestamps, explicit enum values, and opaque public object references. Commercial write requests require `Idempotency-Key`; its actor/command scope and conflicting-payload behavior follow the record above. Publish exact resource paths and field names in their contract task before frontend use. Anonymous login/registration writes also need explicit CSRF protection; do not assume authenticated-session middleware alone protects an anonymous login endpoint.

## Test naming and traceability

Test names include stable identifiers where appropriate, for example `test_EDGE_001_last_unit_has_one_winner` or `test_INV_035_late_receipt_does_not_revive_reservation`. Parameter IDs can cover explicitly enumerated cases; a test name alone does not prove its assertions.

Update `docs/quality/acceptance-catalog.json` with test node IDs, evidence kind, and status. Status is `planned`, `implemented`, or `verified`; only a successful relevant execution can set `verified`. `verified` records a verified revision or evidence reference and must be reevaluated after relevant changes. Tests retain executable mapping in the versioned suite so CI can detect removed or renamed nodes.

Every domain ID must have a substantive behavioral check or an explicit justified review requirement. Privacy, supplier truthful declarations, real-world safety, and legal/financial readiness require operational evidence as well as automated enforcement; do not falsely classify all real-world facts as machine-proven.

## Fixtures and environment

Fixtures use deterministic fictional actors, a fixed timezone-aware clock, integer monetary values, and named policy versions. Factories produce genuinely valid objects through public service setup where possible; tests for invalid persistence deliberately bypass services to prove constraints. Never share mutable fixtures across tests or use production secrets.

HTTP tests verify backend authorization even when UI buttons are hidden. Persistence tests use PostgreSQL; thread/process contention uses independent connections and real commits. Provider adapters use sanitized recorded contracts and controllable fake outcomes, while separate sandbox evidence verifies current assumptions. Tests must not make live financial calls by default.

Resource identifiers are UUID strings generated by PostgreSQL native `uuidv7()`. Numeric legacy identifiers must be resolved through the deliberate migration map; they are not accepted as new API IDs.
